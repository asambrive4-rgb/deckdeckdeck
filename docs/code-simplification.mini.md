# OBEY Code Simplification & Anti-Overengineering

## When to use

- **새로운 기능을 구현할 때**: 불필요한 계층, 과도한 추상화, 미래를 가정한 코드를 사전에 차단.
- **기존 코드를 수정하거나 리팩터링할 때**: 같은 동작을 더 적은 줄 수, 더 얕은 호출 스택, 더 낮은 인지 부하로 개선.
- **코드 리뷰 및 검토할 때**: 불필요하게 장황한 보일러플레이트와 복잡성을 감지하고 제거.

## Primary bias to correct

- **"코드가 길고 클래스/인터페이스가 많을수록 정교하고 견고하다"는 착각을 버려라.**
- 동작과 안전성이 동일하다면, 줄 수가 적고, 개념의 수가 적고, 호출 깊이가 얕고, 읽는 사람이 머릿속에 담아둘 정보가 적은 코드가 최선의 코드다.

## Decision rules (핵심 설계 기준)

### 1. 사변적 일반화(YAGNI) 엄격 금지
- 지금 당장 요구되지 않는 "미래 확장용" 제네릭, 옵션 매개변수, 가상(virtual) 메서드, 추상 베이스 클래스를 만들지 마라.
- 현재 필요한 단 하나의 구체적인 사용 사례에만 집중하라.

### 2. 1회성 인터페이스 및 단일 구현체(Single-impl Interface) 배제
- 구현체가 단 하나뿐이고 단위 테스트 시 Mock/Fake로 대체할 필요가 없는 내부 컴포넌트는 인터페이스(`IFooService`)를 미리 만들지 마라. 구체 클래스(`FooService`)로 직관적으로 작성하라.

### 3. 얕은 래퍼(Pass-through) 및 무의미한 레이어 제거
- 하위 메서드를 단순히 인자만 넘겨주며 호출하는 1줄짜리 포워딩 함수/서비스는 복잡성을 숨기지 못하는 "얕은 모듈"이다. 호출부에서 직접 호출하거나 인라인화하라.
- 단순히 데이터를 옮겨 담기만 하는 중간 DTO/매퍼 클래스를 남발하지 마라.

### 4. 화살표형 깊은 중첩 금지 (Guard Clause 우선)
- 2단계 이상의 `if / else` 중첩은 무조건 Early Return(가드 절)으로 평탄화하라.
- 예외, 유효성 실패, 빈 데이터 등 엣지 케이스를 먼저 리턴하여, 정상 흐름은 들여쓰기 1단계(들여쓰기 없음)로 유지하라.

### 5. 최신 언어 관용구(Idiomatic Syntax)로 압축
- 장황한 루프, 임시 변수, 수동 누적 로직은 언어의 현대적 기능으로 압축하라:
  - C# 예: 패턴 매칭(`is`, `switch expression`), LINQ(`Where`, `Select`, `Any`), Null 조건/병합 연산자(`?.`, `??`), 표현식 본문 멤버(`=>`), 컬렉션 식(`[...]`).
- 코드가 짧아지더라도 가독성을 해치는 난해한 기교(Code Golf)는 지양하되, 표준 관용구를 통해 10줄을 1~2줄로 축약하라.

### 6. 불필요한 임시 변수와 상태 제거
- 결과값을 저장했다가 나중에 리턴하기 위한 임시 변수(`bool flag`, `result`)는 제거하고, 계산 즉시 리턴하라.
- 다른 필드로부터 파생 가능한 값은 별도 상태 필드로 들고 있지 말고 계산 프로퍼티(`=>`)로 표현하라.

### 7. 동작 및 테스트 보존
- 코드 단순화는 외부 동작(Behavior)을 절대 변경해서는 안 된다.
- 기존 단위 테스트가 100% 통과해야 하며, 단순화로 인해 엣지 케이스 처리가 누락되지 않았는지 항상 검증하라.

## Detailed Anti-Patterns & Direct Fixes (구체적 개선 패턴)

| 안티패턴 (지양) | 직접 해결 패턴 (권장) |
| :--- | :--- |
| **깊은 중첩** (`if (a) { if (b) { do(); } }`) | **가드 절**: `if (!a) return; if (!b) return; do();` |
| **단순 전달 래퍼** (`void Run() => _core.Run();`) | 래퍼를 거치지 않고 호출자가 `_core.Run()`을 직접 호출하도록 인라인화 |
| **수동 리스트 누적 루프** (10줄의 `foreach` + `Add`) | **LINQ / 식**: `items.Where(...).Select(...).ToList()` |
| **장황한 null 체크 & 분기** (`if (x != null && x.Y != null)`) | **Null 조건식**: `x?.Y?.DoSomething()` |
| **장황한 switch 문** (`switch(x) { case 1: return A; ... }`) | **Switch 식**: `x switch { 1 => A, 2 => B, _ => C }` |
| **단일 구현체 인터페이스** (`interface IFoo` + `class Foo : IFoo`) | 인터페이스 없이 구체 클래스 `Foo` 단독 정의 (필요 시점에 추출) |
| **상태 플래그 유지** (`var ok = false; if (...) ok = true; return ok;`) | **즉시 반환**: `if (...) return true; return false;` 또는 `return condition;` |

## Trigger rules (작업 시 자동 발동 기준)

- **[기능 추가 시]** 새 파일이나 클래스를 만들 때, "이 계층이 없으면 정말 안 되는가?"를 자문하고, 최소한의 파일과 타입으로 작성한다.
- **[코드 작성 시]** `if`문 안에 또 다른 `if`문이 들어가면 즉시 멈추고 Early Return으로 뒤집는다.
- **[코드 수정 시]** 단순히 아래 계층으로 값을 전달하기만 하는 메서드나 클래스가 보이면 인라인화를 검토한다.
- **[반복문 작성 시]** `new List<T>()`를 선언하고 루프를 돌며 필터링/변환하고 있다면, 표준 선언형 함수(LINQ 등)로 대체한다.
- **[인터페이스 선언 시]** 구현체가 1개뿐이고 다형성이나 테스트 분리가 필요 없다면 인터페이스를 제거하고 구체 클래스로 유지한다.

## Final checklist

- [ ] 새로운 기능을 추가할 때 미래를 위한 불필요한 계층, 래퍼, 인터페이스를 만들지 않았는가?
- [ ] 동일한 동작을 더 적은 줄 수와 더 직관적인 표준 문법으로 달성했는가?
- [ ] 2단계 이상의 들여쓰기 중첩이 가드 절로 평탄화되었는가?
- [ ] 불필요한 임시 변수, 플래그 변수, 얕은 전달 함수가 제거되었는가?
- [ ] 기존 및 신규 기능의 단위 테스트가 모두 정상 통과하는가?
